# Security Policy

## Supported versions

Only the latest minor release line of `mitosis-orchestrator` receives security fixes. Please update to the newest release before reporting, and see [CHANGELOG.md](./CHANGELOG.md) for what changed.

## Reporting a vulnerability

Do not open a public issue for a vulnerability.

Use GitHub private vulnerability reporting: open the **Security** tab of [ivanusto/mitosis-orchestrator](https://github.com/ivanusto/mitosis-orchestrator), choose **Report a vulnerability** (Security Advisories), and describe the problem, the platform (agy, Claude Code or Codex), the plugin version and steps to reproduce.

## Hook permission semantics

These are the behaviours that matter for a security review. They are documented in [README.md](./README.md) and [rules/AGENTS.md](./rules/AGENTS.md).

- **Workspace Guard is opt-in.** It is enabled with `AGY_MITOSIS_AUTO_ALLOW=1`, `CLAUDE_MITOSIS_AUTO_ALLOW=1` or `CODEX_MITOSIS_AUTO_ALLOW=1` (`*_MITOSIS_AUTO_ALLOW=1`). When enabled it auto-approves file and command tools that stay inside the workspace. It prompts (`ask`) for paths outside the workspace, privilege escalation, root deletes, force pushes and shell-piped downloads. Codex has no `ask`, so the same cases are denied there.
- **The workspace command guard is best effort.** It reads the command text with pattern matching, so it is defence in depth and not a sandbox. It cannot see through variable indirection (`set X=...&& type %X%`), interpreters (`python -c`) or scripts that the command runs. The real boundary is the OS sandbox or the permission mode of your agent; keep prompts on for anything you do not want auto-approved.
- **Default behaviour gives no verdict.** With the guard disabled, the Claude Code hook returns `{}`, so your normal permission rules and prompts apply.
- **1.5.0 and earlier skipped permission prompts.** Those versions answered `Bash`, `Read`, `Write`, `Edit` and `SendMessage` calls with `allow`, which Claude Code treats as "skip the permission prompt". This was fixed in 1.5.1. If you ran 1.5.0 or earlier, update.
- **Scout read-only layer.** A `flash-lite-scout` or Codex `explorer` cannot use `Write`, `Edit` or `apply_patch`, whatever its prompt says, and its shell commands must pass an allowlist. The Codex MCP server also starts scouts with `--sandbox read-only` and workers with `--sandbox workspace-write`.
- **The scout command check reads text; it is not a sandbox.** It denies what it cannot read for certain (`$`, backticks and comments outside single quotes, groups, a lone `&`, programs with a path, most environment prefixes, known options that run a program or write a file), so it denies some harmless commands on purpose. Versions before 2.4.1 allowed commands that ran other programs or wrote files, and a white-box review of 2.4.1 found 28 more cases in 7 causes that 2.5.0 closes: `git config --get --no-get` (a write on git before 2.46), `git branch --list --no-list` and `git tag --format --list` (create refs), gpg started by `--show-signature`, `%G` or `%(signature`, `--diff-merges=remerge`, `file -z`, ugrep's `---` spelling of `--config`, and a glob in the `git -C` value that expands into the subcommand slot. Update. It cannot see: execution driven by configuration (`core.fsmonitor`, `diff.external`, textconv, an existing `.ripgreprc`), shell rc files, aliases and functions, a hostile program already on `PATH`, options added by a future tool version (git options were reviewed by hand, not enumerated, so more of the same kind may exist), run time and output size (`cat /dev/zero` passes), or tools other than the ones it is registered for. A glob that expands to a file named like an option is not checked for `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `egrep`, `fgrep`, `stat`, `du`, `cut`, `basename`, `dirname`, `realpath`, `readlink`, `echo`, `nl`, `cmp`, `md5sum` and `sha256sum` (`cat *`, `grep x *`, `tail *` pass; the option tables of `grep` and `tail` still apply to the words you type). It is checked for the other programs, where `src/*.py` and `./*` pass. `git status`, `git diff` and `git describe --dirty` may refresh `.git/index`; this is accepted, not blocked. A Claude Code scout has no OS sandbox behind this check; a Codex scout started through the MCP server runs under `--sandbox read-only`.
- **Scout `git branch --merged` and `--contains`.** Allowed only as `git branch [-a -r -v -vv -i -q] --merged|--contains [REV]`: the option is spelled in full and is the last or second to last word, and REV is one plain word (no leading `-`, glob, `$`, backtick, `%` or brace). `--merged=REV`, abbreviations, any word after REV, and `--no-merged` / `--no-contains` with a name keep the old rules.
- **Codex `write_stdin` and the shell a Codex scout picks.** Codex does not send `write_stdin` to hooks: in 0.166 its `pre_tool_use_payload` returns None by design, so no matcher change can reach it (earlier text said one could; that was wrong). It only writes bytes to a process that already passed the check, and Codex sets `PAGER=cat`, `GIT_PAGER=cat` and `TERM=dumb`. Codex `exec_command` also takes a `shell` argument that the hook cannot see. On Windows, and since 2.5.0 on a POSIX host where `pwsh` or `powershell` is reachable, a Codex scout gets a stricter character set (no quotes, backslashes, redirects, globs, `;` or `&`), because PowerShell and cmd quote differently from POSIX. This strict mode has not been checked against a real `pwsh`, and PowerShell 7 is untested. A Claude scout's shell is bash or zsh (Git Bash on Windows). Fish does not arise: Codex falls back to zsh for fish and Claude Code selects bash or zsh. zsh was not run in the 2.5 verification.
- **Codex hook trust.** Enable the hooks feature and approve the plugin hooks in `/hooks`. **Every plugin update requires a new review on Codex**, even when the hooks file did not change, because Codex computes a content hash over the whole plugin directory (excluding `__pycache__`, `.venv`, `*.pyc` and `*.egg-info`). A hook that is not approved does not run, and the session carries on: older Codex skipped it silently, and `codex exec` on 0.166 showed `hook: ... Failed` and let the subagent run its commands. After each update, open Codex once, accept the review, and check that `hook:` lines show `Completed`. Until then the guard does not run. `scripts/mitosis-doctor.py` compares the hashes from local files (`trust.<event>` and `trust.bundle`) and reports `trust.bundle` FAIL until you accept; that is correct. It never starts Codex. No plugin script writes trust hashes: only you, in Codex, can approve a hook.
- **`MITOSIS_CODEX_YOLO=1` bypasses the sandbox.** It runs Codex subagents with `--dangerously-bypass-approvals-and-sandbox`. Leave it unset unless you deliberately want that.
- **The optional judge sends prompts out.** It is off by default. When `MITOSIS_JUDGE_URL` is set, low-confidence routing decisions send the task prompt to that URL. The prompt is cut to 2000 characters, and secrets, e-mail and IP addresses and home directories are masked before sending. The bearer token (`MITOSIS_JUDGE_KEY`) goes only over https or to a loopback or private-network host unless `MITOSIS_JUDGE_ALLOW_HTTP_KEY=1`. Point it only at an endpoint you trust.

## Opt-in pinning of built-in agents

`CLAUDE_MITOSIS_PIN_BUILTINS=1` (off by default) lets the PreToolUse hook set `model` and `effort` on Claude Code's built-in `Explore` agent and route `general-purpose` like an untyped call. With it on, `Explore` runs on the scout model but does not get the scout Bash allowlist, and its stops do not block or escalate; the SendMessage guard still applies. Its read-only limit comes from Claude Code's own tool list for that agent, not from this plugin. The quality impact of a cheaper model on these built-ins has not been measured and no saving is claimed. The heartbeat counts built-in agent stops by fixed name only (`Explore`, `Plan`, `general-purpose`, `other`), never prompts, paths or text.
